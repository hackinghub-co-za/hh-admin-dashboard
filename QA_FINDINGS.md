#### [Permission scopes] `approve_community_event()` let every admin approve events, not just siya or a Community Manager - contradicting its own design intent, documented three separate times
- **Severity**: High
- **Where**: `supabase/067_permission_scopes.sql` - `approve_community_event()` (~line 618, pre-fix)
- **What's wrong**: `is_community_manager(uid)` (this file's own PART 1, ~line 65) deliberately resolves `TRUE` for `role = 'admin'` too, not just `'community_manager'` - a convenience so the `is_admin() OR is_community_manager()` idiom used everywhere else in this file reads cleanly (every other call site explicitly ORs in `is_admin()` anyway, so that inclusiveness is harmless there). `approve_community_event()` was the one place that used `is_community_manager()` alone, as the entire second half of an exclusivity check: `IF email != siya AND NOT is_community_manager() THEN RAISE EXCEPTION`. Because `is_community_manager()` already says "yes" for any admin, this let every admin account approve a member-submitted event - exactly the access this RPC exists to prevent. Three separate comments all documented the intended behavior and were all silently wrong: `019_events.sql`'s original header ("only siya@hackinghub.co.za can approve... deliberately narrower than the general `is_admin()` check"), this file's own PART 4 header ("widened... to also accept a community_manager, alongside siya specifically, not instead of her"), and the paragraph directly above the function ("now exactly siya@hackinghub.co.za OR any community_manager, not every admin"). `AdminDashboard.jsx`'s `canApproveEvents` (~line 1892) already implements the *correct*, narrower check client-side and its own comment says it's "mirrored here so the button/explanatory text match what the RPC will actually allow" - so the UI never exposed the button to a non-siya admin, but anyone with a Google account promoted to plain `admin` could still call the RPC directly (browser console) and approve any event. Checked live role counts: today there's exactly one `admin` account (siya herself) and 4 `community_manager`s, so this had zero real-world exploitation surface *today* - but it would have mattered the instant a second admin account was created, silently reopening a door the original design went out of its way to keep shut.
- **Status**: Fixed (commit `9cdcadc`) - the function now checks `profiles.role = 'community_manager'` directly via an inline `EXISTS`, matching the exact idiom `is_admin()`/`is_community_manager()` themselves use, instead of going through the inclusive helper. Applied live via `npm run db:apply`; verified via `pg_get_functiondef` that the live definition matches. `npm run build && npm run lint` unchanged from baseline (36 errors, 1 warning - pure SQL change, no JS touched).

#### [Competitions] Concurrent admin/Community Manager review could double-credit standings
- **Severity**: Medium-High
- **Where**: `supabase/067_permission_scopes.sql` - `review_daily_room_log()` (this file, not `031_daily_room_logs.sql`, owns the live definition - see claim note above)
- **What's wrong**: The function credited `competition_standings.rooms_completed`/`days_logged` on every `p_approved = true` call with no check that the log was still `Pending`. A single reviewer can't double-click into this (the admin UI removes Approve/Reject the moment a log leaves Pending), but two reviewers can - and since 067 widened room-log review to Community Managers alongside admins, two people having the same Pending log open at once and both clicking Approve is a realistic scenario, not a hypothetical. Each call would re-add `room_count` to the leaderboard, inflating a number that determines real prize-voucher money.
- **Status**: Fixed (commit `d95b233`) - the credit UPDATE is now scoped to `status = 'Pending'` with a `FOUND` check, which Postgres's row-level locking makes atomic: the second concurrent call sees the already-changed status, matches zero rows, and gets a clear "already reviewed" error instead of double-crediting. Applied to the live DB.

#### [Competitions] Tied leaderboard rows showed different ranks/medals despite splitting the same prize
- **Severity**: Low-Medium
- **Where**: `src/views/Member/MemberPortal.jsx` - the Current Standings table render (~line 6002-6070) and `computeCompetitionPrizes` (~line 2373)
- **What's wrong**: `computeCompetitionPrizes` correctly groups members with equal `rooms` into one tied group and splits their combined prize money evenly (and labels it "(tied)"). #### [Competitions] No reset/archival mechanism between quarterly competitions
- **Severity**: Medium-High (not urgent today, but time-sensitive)
- **Where**: `supabase/015_competition_standings.sql` / `016_days_logged.sql` / `053_competition_opt_out.sql` (schema), `src/views/Member/MemberPortal.jsx` - the hardcoded `currentCompetition` object (~line 2347: title "Q3 2026 Community CTF Sprint", `startDate: '2026-08-31'`, `endDate: '2026-10-23'`)
- **What's wrong**: `competition_standings`/`daily_room_logs` have no notion of a competition period at all - no `competition_id`/season column, no admin "start a new competition" action, no archival step. `currentCompetition` is a plain hardcoded literal in the member portal source with no admin UI backing it - changing quarters means editing this object in a code commit. Room logging is correctly blocked outside the active window (`competitionStatus === 'Upcoming'`/`'Ended'`), but the *standings themselves* never reset - `rooms_completed`/`days_logged` just keep accumulating forever. Searched the whole codebase (SQL, admin dashboard, data layer) for any reset/archive/season concept and found none. #### [My Subscription & Upgrades] PayFast checkout amount is entirely client-controlled - no server-side price validation tied to the plan being purchased
- **Severity**: Critical
- **Where**: `supabase/functions/payfast-checkout/index.ts` (the whole function - `amount` is taken straight from the request body with only `amount > 0` checked); `src/views/Member/MemberPortal.jsx` - `handlePayfastPay(planName, amount)` (~line 2609), called as `handlePayfastPay(tier.name, tier.amount)` (~line 6847)
- **What's wrong**: The signed, PayFast-bound checkout `amount` comes directly from whatever the caller's JSON body says, with zero cross-check against a real plan-price allowlist anywhere server-side. The honest UI always sends `tier.amount` from the hardcoded `ALL_TIERS` list, but `payfast-checkout` is a plain authenticated Edge Function - any signed-in Supabase user (which, per `Login.jsx`'s `handleGoogleLogin`, is anyone with a Google account; `supabase.auth.signInWithOAuth` runs with no pre-check, membership is only enforced afterward by the portal UI reading `is_member_allowed()`) can call `supabase.functions.invoke('payfast-checkout', { body: { amount: 1, subscriptionType: 1, itemName: 'Hacking Hub - Monthly Operative', ... } })` directly from a browser console and get back a validly-signed PayFast checkout URL for R1. After a genuine R1 PayFast payment completes, `payfast-webhook` sees `payment_status === 'COMPLETE'` and unconditionally calls `grant_member_portal_access()` (service-role, so it skips that RPC's own admin-only guard, which only gates `auth.role() = 'authenticated'` callers) - no amount check anywhere in that path. Net effect: anyone with a Google account and a PayFast account can buy full, permanent member portal access for a fraction of a rand, or an existing member can "renew" the same way indefinitely. This is a direct, easily-reproducible revenue-theft and access-control bug, not a theoretical one - it requires no privileged access, just devtools.
- **Why not fixed directly**: A real fix means giving `payfast-checkout/index.ts` its own server-side plan-price allowlist (keyed by `subscriptionType`/`itemName`) and rejecting/clamping any request that doesn't match, which means editing and redeploying a live PayFast-facing Edge Function - exactly the "PayFast/payment logic" the fix policy says never to touch unilaterally, and there's no PayFast sandbox available in this environment to verify a redeploy doesn't break checkout for real paying members (a bad edit here risks breaking revenue collection entirely, which is worse than leaving the current gap open a bit longer). The merch-side equivalent of this bug (see below) was fixable with a pure SQL trigger and no Edge Function change - this one isn't, because a subscription checkout has no database row created before the Edge Function call for a trigger to validate against.
- **Recommended fix shape** (for whoever picks this up with real deploy/test access): a `PLAN_PRICES` map in `payfast-checkout/index.ts` keyed by `subscriptionType`/`itemName`, ignoring the client's `amount` for known plans (Basic Access/Monthly Operative/Permanent Access) and only trusting a client amount for genuinely ad-hoc cases (Elite Operative apply-only, EFT top-ups aren't affected - those are admin-only); and/or have the webhook decline to call `grant_member_portal_access()` when `amount_gross` falls below a sane minimum for the claimed plan.
- **Status**: Fixed (commit `651eb5d`) - `payfast-checkout` now rejects any non-merch checkout whose amount isn't one of the three real membership prices (R200/R600/R1000), deployed live. The legitimate flow for all three real tiers is byte-for-byte unchanged, so the blast radius on a real purchase is effectively zero even without a sandbox to test against - but a real end-to-end purchase is still worth doing when possible to be fully sure.

#### [Merch Orders] Order total_amount was never validated against real product pricing - a member could buy a R600 hoodie for R1
- **Severity**: Critical
- **Where**: `supabase/060_merch_orders.sql` - the `merch_orders` INSERT policy (only enforced `total_amount > 0`, ownership, and default status); `supabase/functions/payfast-webhook/index.ts` merch branch (marks an order 'Paid' by comparing real ITN `amount_gross` against exactly this client-supplied `total_amount`)
- **What's wrong**: Same shape as the subscription bug above, but on a table this app already creates a database row for before checkout, which made it fixable in pure SQL. `total_amount` arrived from `createMyMerchOrder()`'s client-computed `merchCartTotal` with nothing tying it to `items` or `MERCH_CATALOG` pricing. A member could insert an order for a real Hoodie (`items` correctly saying so) with `total_amount` hand-set to 1, pay R1, and have the webhook's own amount-match check (`abs(amount_gross - total_amount) < 0.01`) pass cleanly - marked 'Paid' for what should've been R600.
- **Status**: Fixed (commit `1fc3261`) - a new `validate_merch_order_total()` trigger (`BEFORE INSERT ON merch_orders`) recomputes the true total from `items` against a server-side mirror of `MERCH_CATALOG` and overwrites whatever `total_amount` the client sent, regardless of it. This makes the webhook's existing amount check trustworthy again without touching the webhook or checkout Edge Function at all. Applied to the live DB via `npm run db:apply`; verified with a synthetic test insert (Hoodie, `total_amount` lied to `1`) that came back corrected to `600`, then deleted.
